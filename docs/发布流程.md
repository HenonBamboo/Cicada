# 发布流程

本项目发布 Windows 11 x64 直接运行 EXE 和便携 ZIP，不生成安装向导。

1. 更新 `CHANGELOG.md`、README 和隐私说明，保持 npm、Cargo、Tauri 三处版本一致。确认第三方声明覆盖锁定依赖，锁文件的 SHA-256 已更新。
2. 先用 `scripts/clean-release.ps1 -Preview` 核对清理路径，再运行清理。脚本只删除白名单内未跟踪的生成物，拒绝目录联接、符号链接和跟踪文件；不使用 `git clean`，不触碰 `%APPDATA%\Cicada`。
3. 运行 `npm ci` 恢复锁定依赖，按本次改动完成类型检查、聚焦测试和 Windows 11 验收。不要扩大到 Windows 10 或安装器。
4. 将 Ed25519 PEM 私钥正文保存到 Windows 用户环境变量 `CICADA_UPDATE_PRIVATE_KEY`，签名脚本会自动读取；也兼容 `CICADA_UPDATE_PRIVATE_KEY_PATH` 指向仓库外的私钥文件。必须与源码 `updater/public-key.txt` 匹配；私钥不能写入仓库、日志或发布包，原文件保留在仓库外受保护的位置作备份。设置仅有本仓库发布权限的 `GITCODE_TOKEN`，并确认 `gh auth status` 正常。
5. 打包：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/package.ps1 -OutputDirectory "$env:TEMP\Cicada-release-0.2.3"
   ```

   输出目录必须为空。默认使用系统临时目录，构建保持 `--no-bundle`；已完成当前源码的 Release 构建时可用 `-SkipBuild` 只执行打包和签名。

6. 确认输出目录恰好五个文件：版本化 EXE、便携 ZIP、`SHA256SUMS`、`latest.json`、`latest.json.sig`。ZIP 包含 EXE、许可证、README、隐私说明、更新记录和第三方声明。更新清单只描述单 EXE，由应用内置公钥验证签名，随后验证大小与 SHA-256。
7. 保留临时发布目录，退出验证进程后再次运行仓库清理。检查 `git status`，只提交本次发布源码、文档、锁文件和必要的生成权限声明；创建对应标签，例如 `v0.2.3`。
8. GitHub `origin` 使用 `git@github.com:HenonBamboo/Cicada.git`；`gitcode` 使用 `git@gitcode.com:HenonBamboo_YYJ/Cicada.git`。上传使用 PowerShell 7；准备仓库外的发布说明文本后运行：

   ```powershell
   pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/publish.ps1 -ArtifactDirectory "$env:TEMP\Cicada-release-0.2.3" -NotesFile "$env:TEMP\Cicada-release-notes.md"
   ```

9. 发布脚本推送同一提交和标签，在两端上传五个文件，逐个重新下载并核对 SHA-256，再确认 GitCode 的 latest 指向新版本。只有两端核对成功，才删除临时发布目录与发布说明文件。失败时保留产物用于恢复，不重新生成一套不同签名的文件覆盖已发布版本。

应用启动只从 GitCode 检查更新，不包含平台 Token。`0.2.3` 已轮换更新签名密钥，`0.2.2` 及更早版本须手动下载并覆盖本版一次；本版之后可确认后直接替换 EXE。失败时保留或恢复旧 EXE；数据目录和 Windows 凭据不随程序替换而移动。

发布目录、依赖和构建缓存均不提交到 Git。更新清单签名不等于 Windows 代码签名。未完成的检查和平台发布状态应如实说明，不能仅凭构建成功宣称完整发布。
